# M3 wave 5: `apps/web/components/shared` + `components/ui` date pickers (read-only, 2026-11-14)

Analysis only; no component was changed. Scope: the inventory's wave 5 row (`data-table`, `filter-bar`,
`form-sheet`, `bulk-action-dock`, `infinite-scroll-footer`, date pickers, `money-*`), plus two components found
during this analysis that the inventory row didn't name individually (`drilldown-filter-bar` +
`drilldown-filter-popover`, `entry-status-date-picker`). 11 files in total. **Unlike every prior wave, `packages/ui`
has no copy of any of these** — this is "move + create" for all of them, the same shape as wave 3's `pagination`,
not a diff.

## Result in one line

**3 of 11 are already eligible with zero seam** (`bulk-action-dock`, `form-sheet`, `drilldown-filter-bar` +
`drilldown-filter-popover`). **The rest split into three seam shapes, each needing one owner decision**: a locale
prop/context for 5 components that only need a `Locale` string (`money-text`, `money-input`, `date-picker`,
`date-time-picker`, `entry-status-date-picker`), an explicit `labels` prop for 1 component that needs 4 translated
strings (`infinite-scroll-footer`), and a URL-state injection point for 2 components deeply coupled to `nuqs`
(`filter-bar`, `data-table`). **No admin consumer or look-alike exists for any of the 11** — zero admin-impact risk
this wave, unlike wave 3.

## The three seam shapes

### 1. Locale-only (`money-text`, `money-input`, `date-picker`, `date-time-picker`, `entry-status-date-picker`)

All five only need the active `Locale` (`"bn" | "en"`) to call a pure formatter (`formatMoney`/`formatNumber`/
`formatDate` in `apps/web/lib/format.ts` — plain `Intl` wrappers, no next-intl coupling). Two ways to inject it:

- **(a) Required prop.** Shared component takes `locale: Locale` directly; every call site (60 + 8 + 33 + 4 + 2 =
  107 call sites across the 5 components) gains a `locale={locale}` prop, where web's wrapping component calls
  `useLocale()` once and threads it down, or every leaf call site calls `useLocale()` itself.
- **(b) Small context (principle 5's own suggestion).** `packages/ui` ships a tiny `LocaleProvider`/`useLocale()`
  (not next-intl's own hook — a package-local one), `apps/web`'s root layout wraps once near next-intl's own
  provider, reading next-intl's `useLocale()` and forwarding it in. Shared components call the package-local hook
  internally; zero per-call-site changes beyond the import swap (same blast radius as every other wave's swap PR).

The pure formatters themselves (`formatMoney`, `formatNumber`, `formatDate` — `lib/format.ts` lines 20-39) would
need to move into `packages/ui`'s own `lib/`, duplicated or re-exported; `lib/format.ts` also holds
`formatRelativeTime`/`formatPct`/`formatBusinessDay`, which nothing in this wave needs, so only the 2-3 functions
each component actually calls would move, not the whole file.

**(b) is the recommendation** — it matches principle 5's own wording and keeps every call site's diff to an import
line, same as every prior wave's swap PR, rather than a 107-site prop-threading change.

### 2. Explicit labels (`infinite-scroll-footer`)

Only 4 short strings, no locale-dependent formatting. A `labels` prop (`{ loading, error, end, retry, loadMore }`,
`end` taking a `count` render function or template string) is the direct application of principle 5's "inject
labels... through props" — no default baked into the shared package, so there's no silent wrong-language
fallback if a caller forgets to pass it. All 16 web call sites would need the prop added, **unless** web keeps a
thin wrapper (`apps/web/components/shared/infinite-scroll-footer.tsx` becomes ~10 lines: calls `useTranslations`,
forwards the 4 strings to `@rakhal/ui/shared/infinite-scroll-footer`) — in which case the 16 call sites don't
change at all, but web's `components/shared` folder keeps one file instead of being fully emptied, a first for
this migration (every prior wave deleted the local file outright).

**Owner decision needed**: thread `labels` through all 16 call sites, or keep a thin translating wrapper in web?

### 3. URL-state coupling (`filter-bar`, `data-table`)

Both use `nuqs`'s `useQueryState` in multiple internal sub-components, not just once at the top — `filter-bar` in
3 separate places (`useChecklistValues`, `SearchInput`, `FilterSelect`), `data-table` for its sort param. This
isn't a locale/labels injection — it's "does this component own its own URL-synced state, or does the caller own
it and pass `[value, onChange]` down." Genuinely needs a design change, matching the plan doc's own wording for
this wave ("needs a seam"). Two shapes:

- Keep each sub-piece's state-reading as an internal detail, but make the *hook* itself injectable (a
  `useQueryState`-shaped prop/parameter each caller can override — `nuqs`'s own hook by default in
  `apps/web`, something else wherever `packages/ui` is consumed outside this app).
  **Owner decision needed**: is this worth building now, or does `filter-bar`/`data-table` stay in `apps/web`
  (same "leave it, record why" option principle 2's "when to stop" section allows) until a second consumer
  actually needs them?

## Proposal

### Order, lowest risk first

Phase 1 (zero seam, same shape as every eligible wave 1-3 swap):
1. `bulk-action-dock` (6 files)
2. `form-sheet` (13 files)
3. `drilldown-filter-bar` + `drilldown-filter-popover` (3 files) — adds `motion/react` to `packages/ui`'s deps

Phase 2 (locale seam — one context, built once, unblocks 5 components):
4. Build the package-local `LocaleProvider`/`useLocale()` in `packages/ui`, wire it once in `apps/web`'s root
   layout.
5. Move `money-text` (60 files), `money-input` (8 files) — pure locale + formatter, no translated strings.
6. Move `date-picker` (33 files), `date-time-picker` (4 files) — locale + 2 translated strings (`today`/`clear`)
   for `PickerFooter`, same labels-injection question as phase 3 but only 2 strings.
7. Move `entry-status-date-picker` (2 files) — after `date-picker`, since it imports `PickerFooter`.

Phase 3 (labels seam — one decision, one component):
8. `infinite-scroll-footer` (16 files) — thread `labels` prop, or keep a thin web-side translating wrapper.
9. `data-table` (22 files) — can only move after `infinite-scroll-footer` does (imports it) and after the
   nuqs decision below.

Phase 4 (needs the URL-state design decision, or stays deferred):
10. `filter-bar` (7 files), `data-table`'s own sort param — resolve per the owner decision above, or leave both
    in `apps/web` and record why, per principle 2's "when to stop."

### Owner decisions needed

1. **Locale seam**: build the small `LocaleProvider` context in `packages/ui` (recommended — zero per-call-site
   changes) or thread `locale` as a required prop through all 107 call sites?
2. **`infinite-scroll-footer` labels**: thread a `labels` prop through all 16 call sites, or keep a thin
   translating wrapper in `apps/web/components/shared` (first component this migration wouldn't fully empty
   from the consumer app)?
3. **`filter-bar`/`data-table` URL-state**: worth an injectable-hook seam now, or leave both in `apps/web` and
   revisit if/when `apps/admin` needs them (no admin consumer today, unlike every wave-3 reconciliation)?
4. Batching: one PR per component vs a few batched PRs, as with every prior wave — your call.

## What this analysis did not check

Whether `packages/ui` already has (or should gain) a documented pattern for app-provided context providers —
this would be the first one. Whether `motion/react` is already a `packages/ui` peer/dependency elsewhere (it
isn't, per `package.json`) or needs adding. No unit test was run beyond what's already green on `main`.
