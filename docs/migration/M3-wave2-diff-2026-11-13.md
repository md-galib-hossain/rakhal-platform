# M3 wave 2: diff of `packages/ui` against `apps/web/components/ui` (read-only, 2026-11-13)

Analysis only; no component was changed. Compared on `main` at `2b64617` (after wave 1, PRs #2 to #13).
Scope: every file that exists in both `apps/web/components/ui` and `packages/ui/src/components/ui` after wave 1
(19 components, the rest of the 03 plan's "wave 2" and "wave 3" `ui/*` lists). `components/shared/*` (wave 4/5) is
not covered here.

## Result in one line

**17 of 19 are identical apart from the import lines** (`cn` path, and in four files the sibling imports `./x`
versus `@/components/ui/x`). **Two have real differences, and in both the web copy is ahead of the shared copy**
(`tabs`, `labeled-field`), so "web wins" means porting web's behaviour into `packages/ui` first. **One component
(`combobox`) has zero call sites in web and in admin.** **Two web-only files** (`date-picker`, `date-time-picker`)
import `@/lib/format` and `@/lib/constants/i18n`, so they are not eligible and stay in `apps/web`.

Nothing in the 19 imports `features/*`, `next-intl` or `nuqs`. Third-party deps are all already in
`packages/ui/package.json` (radix, cva, lucide, cmdk, sonner, next-themes, react-day-picker, date-fns).

### The two real differences

`tabs`: web's `TabsTrigger` takes `onClick` and, when the clicked tab is not already active, dispatches a synthetic
`mousedown` before calling the caller's `onClick`. That is a behaviour fix (activating a tab on keyboard or
programmatic click through Radix, which listens to `mousedown`). The shared copy lacks it. Admin has no tabs call
site, so porting is invisible to admin.

`labeled-field`: web is a superset of shared and has diverged in ways that change semantics.
- New props `inputClassName`, `containerClassName`, and `error` on `LabeledSelectTrigger` (typed as the exported
  `LabeledSelectTriggerProps`).
- `className` goes to the **container** in web, to the **input** in shared. Same prop name, different target: the
  shared version must adopt web's meaning, and nothing in admin uses it (0 files), so there is no consumer to break.
- Styling: web adds `min-h-[56px]`, `has-[:disabled]` opacity and cursor, `justify-center`, `select-none`, and a
  destructive border on error.

### `combobox`

Zero imports in web and in admin (the `role="combobox"` hits elsewhere are other components). Web's copy already
imports `Button` from `@rakhal/ui`. Owner decision: delete both copies (dead code) or keep the shared copy for later.

## Coverage method (how "Gate today" was measured)

The components have no `data-slot` markers, so rendering could not be read off the DOM directly. Temporarily (not
committed, reverted) every `cn("...")`/`cva("...")` string in these 19 files was prefixed with a unique inert class
`zz-<component>`, the app was built, the gate specs ran in the `desktop-light` project, and the `zz-*` classes in
the DOM at the end of each test were recorded:

| Screen | Components present |
|---|---|
| dashboard | avatar, select, input |
| animals list | avatar, input, table, chip |
| add-animal sheet | avatar, input, table, chip, sheet, labeled-field, select |
| animal groups (delete confirm) | avatar, input, table, chip, sheet |
| account menu (switch screen) | avatar, select, input, dropdown-menu |
| report wizard (final step) | avatar |
| login / register / forgot-password | floating-input |

Caveats: it records the last state of each test only (the wizard's earlier steps are not sampled); a class on an
element proves it rendered, not that every variant and state is compared; `sonner` has no `cn` string, so it cannot
be tagged and is assumed absent (the Toaster renders nothing until a toast fires). Notably the "confirm dialog"
screen is a `sheet`, so **`dialog` is not covered at all**.

### Reconciliation decisions for the owner

1. `tabs` and `labeled-field`: confirm web wins (shared adopts web's code verbatim). Admin has no users of either,
   so no admin rendering change is expected.
2. `combobox`: delete both copies, delete only the web copy, or leave as is.
3. Batching: wave 1 was one PR per component at about 7 minutes of CI each, run in series because overlapping
   import lines conflict (#5 hit that). For the 16 mechanical swaps, one PR per component is 16 PRs. Alternative:
   batch the identical, covered components into a few PRs (for example avatar+table+chip, then
   floating-input+input+select, then sheet+dropdown-menu). Same checks per PR; fewer merges, slightly less
   isolation. Your call.
