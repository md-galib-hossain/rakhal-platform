# Security Report Explanation

For easier reading, open a generated `.md` report, copy the full markdown content, then paste it into:

```text
https://markdownlivepreview.com/
```

This shows the report with tables and headings rendered in a browser preview.

Security reports are generated by `npm run security` into:

```text
scripts/security/reports
```

Each timestamped markdown report uses:

```text
security-report-YYYY-MM-DD_HH-mm-ss.md
```

The most recent report is also copied to `latest.md` and `latest.json`.

## Report Sections

The report starts with project metadata, branch, commit, generated time, deployment decision, and an overall security result written in plain language. It then shows:

- Dashboard Summary
- Docker Scanner Checklist
- Scan Scope
- Severity Meanings
- Status Meanings
- Confidence Meanings
- Check Results
- Findings Summary
- Finding Details

## Dashboard Metrics

The dashboard shows:

- Overall Security Result

- Open Issues
- Needs Review

## Scan Scope

The Scan Scope section shows what the local suspicious-code scanner included. It lists top-level folders only, so `src` means `src` and its scanned nested folders. Files outside those folders are listed under included root files. The section also shows ignored folders, ignored report paths, scanned extensions, extra scanned file names, and total scanned file count.

## Docker Scanner Checklist

This section shows whether Docker-based gitleaks, Semgrep, and ClamAV are on or off.

- `[x] ON` means Docker was available and the scanner command ran.
- `[ ] OFF / NOT CONFIGURED` means the scanner did not run.

The `Status` column explains the scan result: `PASSED`, `FAILED`, or `SKIPPED`.

## Overall Security Result

`FAIL - Do not deploy. One or more CRITICAL or HIGH security issues are open.`

This means the release should stop until the highest-risk findings are fixed, reviewed, or formally accepted by the responsible security/technical owner.

`WARNING - Review before deploy. Only MEDIUM or LOW security issues are open.`

This means there are no open critical/high findings, but the team should still review the remaining issues before release.

`PASS - No active risky findings were detected by this scan.`

This means the scan did not find active risky issues. It does not prove the application is perfectly secure.

## Finding Details

Each finding includes:

- Finding ID
- Title
- Detected By
- Severity
- Status
- Confidence
- Category
- File path
- Line number when available
- Function name or scope when detectable
- Rule ID
- Why this matters
- Evidence or matched code snippet
- Recommended fix
- Suggested owner/action
- First seen
- Last seen
- Occurrence count

`Detected By` tells you which scanner raised the finding, such as `gitleaks`, `Semgrep`, `ClamAV`, `npm audit`, or `Built-in Suspicious Code Scan`.

Scanner/tooling failures are reported separately from confirmed security issues. For example, if Docker-based gitleaks fails before returning parseable output, the report should say the secret scanner could not complete. That means the scan is incomplete; it does not automatically mean a leaked secret was found.

## Tracking The Same Issue Across Reports

Finding IDs use:

```text
SEC-{CATEGORY}-{SEVERITY}-{HASH}
```

The hash is based on category, file path, line number, rule ID, and title. The tracker file keeps first seen, last seen, and occurrence count so reviewers can see whether an issue is new, recurring, fixed, ignored, or a regression.

## Handling False Positives

If a reviewer confirms that a finding is safe, mark it as `FALSE_POSITIVE` in the tracker. If the team accepts the risk or intentionally skips the finding, mark it as `IGNORED`. Use these statuses carefully and keep the evidence in code review or an issue tracker.

## Marking Fixed Or Ignored

When a previously active finding is no longer detected, the runner marks it `FIXED`. If a previously fixed finding appears again, it becomes `REGRESSION`. Allowlisted scanner findings are tracked as `IGNORED` because they are intentionally accepted for visibility.

## Examples By Severity

`CRITICAL`: exposed production secret, malware signature match, dangerous shell command, credential-stealing pattern.

`HIGH`: hardcoded token, unsafe `eval`, risky shell execution, insecure authentication logic.

`MEDIUM`: weak validation, missing rate limit, suspicious dependency usage, dynamic require usage.

`LOW`: minor hardening concern or best-practice warning.

`INFO`: allowlisted finding or informational scanner output.

## Sample Finding

### SEC-SECRETS-CRITICAL-A91F3C

Severity: CRITICAL  
Status: OPEN  
Confidence: CONFIRMED  
Category: SECRETS  
File: `.env`  
Line: 12  
Rule: `hardcoded-aws-secret`

Why this matters:
AWS secret keys can allow attackers to access cloud resources.

Recommended fix:
Immediately revoke the leaked key, create a new one, and store it in a secure secret manager.
